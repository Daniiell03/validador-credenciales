Guía de laboratorio — Construya su primer pipeline de CI/CD

Tecnológico de Costa Rica · Escuela de Ingeniería Electrónica · Taller de Sistemas Embebidos
Mini-taller: Integración y entrega continua de software embebido · Caso Jenkins

Todos los comandos están verificados sobre WSL2 con Ubuntu 24.04, Docker Engine 29 y Jenkins LTS. El trabajo se realiza en parejas: cada integrante ejecuta su propio Jenkins, pero ambos publican al mismo repositorio. Esa es exactamente la situación que la integración continua existe para resolver.

Antes de empezar

Convenciones

$lo escribe usted en la terminal. No copie el símbolo.
#comentario explicativo. No lo escriba.
>salida esperada del comando.

Todo el trabajo vive en ~/validador-ci. Los integrantes de la pareja se identifican como A y B; decidan ahora quién es quién.

Cada bloque tiene dos botones. Copiar lleva el bloque completo, comentarios incluidos. Solo comandos descarta comentarios y salidas esperadas: es el que conviene para pegar directo en la terminal.

Advertencia — genere el token antes de la sesión

GitHub dejó de aceptar contraseñas para operaciones de Git en 2021. Necesita un token de acceso personal, y generarlo en clase consume varios minutos por persona.

Vaya a Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new token, marque el alcance repo y guárdelo: solo se muestra una vez.

Verificación rápida — hágala antes que nada

bash

Si falta algo

Herramientas de compilación, control de versiones y el editor:

Docker Engine con Compose v2, desde el repositorio oficial:

  | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg

echo "deb [arch=$(dpkg --print-architecture) \
signed-by=/etc/apt/keyrings/docker.gpg] \
https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" \

sudo apt install -y docker-ce docker-ce-cli containerd.io \
                    docker-buildx-plugin docker-compose-plugin

Para no anteponer sudo a cada comando de Docker:

2 Levante Jenkins en un contenedor 10 min
bash · ambos 
cd ~/validador-ci/docker
DOCKER_BUILDKIT=0 docker build -t jenkins-validador:v1 .
docker compose up -d --no-build
docker compose ps

La construcción tarda unos minutos la primera vez.

Advertencia — error conocido en WSL2

Si docker build falla con bind source path does not exist: /usr/lib/wsl, es BuildKit intentando montar una ruta que no existe en su WSL. Por eso el comando lleva DOCKER_BUILDKIT=0 delante: usa el constructor clásico y evita el problema.

Por qué hace falta un Dockerfile propio

Ábralo y mire las líneas del apt-get install:

bash 
cat ~/validador-ci/docker/Dockerfile

La imagen oficial de Jenkins incluye Java y el servidor, pero no incluye compilador de C. Si el pipeline va a ejecutar make, el entorno de construcción tiene que existir dentro de la imagen. Compruébelo:

bash 
docker exec jenkins-validador bash -c \
  "gcc --version | head -1; make --version | head -1; cppcheck --version"
> gcc (Debian 14.2.0-19) 14.2.0
> GNU Make 4.4.1
> Cppcheck 2.17.1

Desbloquee Jenkins

bash 
docker exec jenkins-validador \
    cat /var/jenkins_home/secrets/initialAdminPassword

Abra el navegador en http://localhost:8080. Desde WSL puede lanzarlo así:

bash 
explorer.exe "http://localhost:8080"

En el asistente:

  1. Pegue la clave que imprimió el comando anterior.
  2. Elija Select plugins to install y luego None: ya vienen precargados desde el Dockerfile.
  3. Cree su usuario administrador. Anote sus credenciales.
  4. Deje la URL por defecto y guarde.
Nota — la configuración no se pierde

El docker-compose.yml persiste /var/jenkins_home en un volumen nombrado. Puede detener el contenedor con docker compose down y volver a levantarlo sin perder usuario, trabajos ni historial.

B descargó el material en el paso 1, pero esa copia no tiene historial de Git ni conexión con el repositorio de la pareja. El rm -rf la descarta y el clone trae la versión buena.

Si B ya había modificado algo, cópielo antes a otro sitio: cp -r ~/validador-ci ~/respaldo-b.

4 Conecte Jenkins al repositorio 7 min

Ambos integrantes hacen este paso, cada uno en su propio Jenkins.

En http://localhost:8080: Nueva Tarea → escriba validador-ci → elija Pipeline → OK. Baje hasta la sección Pipeline, al final del formulario:

CampoValor
DefinitionPipeline script from SCM
SCMGit
Repository URLla URL del repositorio de la pareja
Credentials- none - (el repositorio es público)
Branch Specifier**/*
Script PathJenkinsfile

Guarde y pulse Construir ahora.

Advertencia — el comodín es **/*, no **

Con ** a secas el trabajo no encuentra ninguna rama y el build sale en rojo. El comodín hace falta porque a partir del paso 5 van a trabajar con ramas y Jenkins debe construirlas todas, no solo main.

Qué debe ver

El build queda AMARILLO (inestable), no rojo ni verde:

salida de consola
> OK: binario en build/bin/validador-credenciales (version 0.1.1)
> [ FALLA ] test_formato_acepta_ocho_digitos
> Resumen: 1 pruebas, 1 fallas
> Setting overall build result to UNSTABLE
> Stage "Empaquetar" skipped due to when conditional
> Finished: UNSTABLE
Nota — amarillo no es lo mismo que rojo

Rojo (FAILURE): el código no compiló. Está roto.

Amarillo (UNSTABLE): compiló, pero el comportamiento no es el esperado. Una prueba falló.

Note además que Empaquetar y Entregar se omitieron. Nadie lo decidió: lo decidió la condición when del Jenkinsfile. No se empaqueta código que no pasó las pruebas.

El pipeline se dispara solo

El Jenkinsfile incluye un bloque triggers que consulta el repositorio cada dos minutos. Después de esta primera ejecución manual, ya no necesita pulsar Construir ahora: basta con publicar y esperar. Lo reconocerá porque el registro empieza con Started by an SCM change.

c · reemplace estas dos funciones 
int cred_formato_valido(const char *uid)
{
    size_t i;

    if (uid == NULL) {
        return 0;
    }
    if (strlen(uid) != CRED_LONGITUD) {
        return 0;
    }
    for (i = 0u; i < CRED_LONGITUD; ++i) {
        if (uid[i] < '0' || uid[i] > '9') {
            return 0;
        }
    }
    return 1;
}

int cred_checksum(const char *uid)
{
    size_t i;
    int suma = 0;

    if (!cred_formato_valido(uid)) {
        return -1;
    }
    for (i = 0u; i < CRED_LONGITUD - 1u; ++i) {
        suma += uid[i] - '0';
    }
    return suma % 10;
}

6 Pull request y revisión cruzada 10 min

En GitHub, cada uno abre un pull request de su rama hacia main:

  1. Entre al repositorio. Aparece un aviso amarillo con su rama recién publicada.
  2. Pulse Compare & pull request.
  3. Verifique que va de su rama hacia main.
  4. En la descripción, explique en una o dos líneas qué hizo.
  5. Pulse Create pull request. No lo fusione todavía.

Después intercambien: cada uno abre el PR del otro, va a la pestaña Files changed y lee el código del compañero. Pregunte lo que no entienda.

Fusionen primero el de A con Merge pull request → Confirm merge, y después el de B.

Nota — observe el pipeline entre una fusión y la otra

Tras fusionar el PR de A, main tiene la implementación pero solo la prueba de ejemplo: el build queda verde y produce artefacto.

Tras fusionar el de B, entran siete pruebas más. Si la implementación es correcta, sigue verde. Si algo no coincide con la especificación del Anexo A, aparece en amarillo señalando exactamente qué prueba falló.

Eso es integración continua. Dos personas trabajaron por separado y el pipeline verificó la combinación en minutos.

Actualicen su copia local:

cd ~/validador-ci
git checkout main
git pull
make clean && make test      # las 8 pruebas deben pasar

7 El choque — conflicto de fusión 8 min

Este paso provoca un conflicto a propósito. Háganlo exactamente como se indica.

A

bash · integrante A 
cd ~/validador-ci
git checkout main && git pull
git checkout -b uid-largo
sed -i 's/#define CRED_LONGITUD   8u/#define CRED_LONGITUD  10u/' src/credencial.h
grep CRED_LONGITUD src/credencial.h    # confirme el cambio
git commit -am "Amplia el UID a 10 digitos"
git push -u origin uid-largo

B

bash · integrante B 
cd ~/validador-ci
git checkout main && git pull
git checkout -b uid-corto
sed -i 's/#define CRED_LONGITUD   8u/#define CRED_LONGITUD   6u/' src/credencial.h
grep CRED_LONGITUD src/credencial.h    # confirme el cambio
git commit -am "Reduce el UID a 6 digitos"
git push -u origin uid-corto
Nota — alternativa con editor

El sed es un atajo. Si prefiere verlo, abra el archivo con nano src/credencial.h, busque CRED_LONGITUD con Ctrl+W y cambie el número a mano.

Abran los dos pull requests. Fusionen el primero: entra sin problema. Al intentar el segundo, GitHub muestra This branch has conflicts that must be resolved.

Resuélvanlo desde la web:

  1. Pulse Resolve conflicts.
  2. GitHub marca la zona en disputa con <<<<<<<, ======= y >>>>>>>.
  3. Borre esas marcas y deje una sola línea con el valor acordado.
  4. Mark as resolved → Commit merge.

Después dejen el valor en 8u para el resto del taller:

bash · ambos 
cd ~/validador-ci
git checkout main && git pull
grep CRED_LONGITUD src/credencial.h    # debe decir 8u
make clean && make test
Nota — qué acaba de pasar

Git no puede decidir cuál de las dos versiones es correcta, porque ambas son sintácticamente válidas. Solo ustedes saben cuál refleja el requisito.

En un equipo real esto ocurre a diario. Cuanto más tiempo pasa una rama sin integrarse, más grande y más difícil es el conflicto. De ahí el nombre: integración continua.

c · reemplace cred_autorizar 
cred_resultado_t cred_autorizar(const char *uid,
                                const char *permitidas[],
                                size_t n)
{
    size_t i;
    int digito;

    /* 1. formato */
    if (!cred_formato_valido(uid)) {
        return CRED_ERR_FORMATO;
    }

    /* 2. checksum: el ultimo digito debe coincidir */
    digito = cred_checksum(uid);
    if (digito < 0 || uid[CRED_LONGITUD - 1u] - '0' != digito) {
        return CRED_ERR_CHECKSUM;
    }

    /* 3. lista de permitidas */
    if (permitidas == NULL) {
        return CRED_ERR_NO_AUTORIZADA;
    }
    for (i = 0u; i < n; ++i) {
        if (permitidas[i] != NULL && strcmp(uid, permitidas[i]) == 0) {
            return CRED_OK;
        }
    }
    return CRED_ERR_NO_AUTORIZADA;
}

9 Modifique el pipeline 10 min

Hasta ahora usaron un pipeline que les vino dado. Ahora lo van a modificar.

git checkout -b pipeline-analisis

Abran el pull request, revísenlo y fusiónenlo. Observen en Jenkins: la vista de etapas ahora tiene una columna más.

Nota — esto es Pipeline as Code

Acaban de cambiar el proceso de construcción con un commit. Quedó revisado por su compañero, registrado en el historial y es reversible.

Si el pipeline estuviera configurado desde formularios de la interfaz web, ese cambio no tendría autor, ni fecha, ni revisión, ni forma de deshacerse.

Desafío opcional: haga que Analizar solo se ejecute en main, copiando el bloque when de Empaquetar.

Nota — la red de seguridad

Un cambio de un carácter, sintácticamente válido, alteró el comportamiento de un sistema de control de acceso. Las pruebas lo detectaron y el pipeline impidió que se produjera un artefacto entregable.

En software embebido eso importa más que en la web: un firmware defectuoso puede llegar a miles de dispositivos que nadie va a actualizar en años.

int cred_checksum(const char *uid)

Suma los valores numéricos de los primeros CRED_LONGITUD - 1 caracteres y devuelve esa suma módulo 10. Con "12345678": 1+2+3+4+5+6+7 = 28, y 28 mód 10 = 8. El octavo carácter no participa: es el dígito que se verifica.

EntradaRetorno
"12345678"8 — suma 28
"11111117"7 — suma 7
"1234567A" · NULL-1

cred_resultado_t cred_autorizar(...)

Aplica tres verificaciones en este orden y devuelve el error de la primera que falle:

#VerificaciónSi falla, devuelve
1Formato válidoCRED_ERR_FORMATO
2El último dígito coincide con el checksum calculadoCRED_ERR_CHECKSUM
3El uid aparece en permitidasCRED_ERR_NO_AUTORIZADA

Si las tres se cumplen, devuelve CRED_OK.

Nota — casos límite

uid == NULL → CRED_ERR_FORMATO.

permitidas == NULL o n == 0 → ninguna credencial está autorizada, de modo que una credencial bien formada y con checksum correcto devuelve CRED_ERR_NO_AUTORIZADA, no CRED_OK.

Una credencial con formato inválido y ausente de la lista devuelve CRED_ERR_FORMATO, porque esa verificación va primero.

 && apt-get install -y --no-install-recommends \

USER jenkins

La imagen oficial trae Java y el servidor, pero no el compilador. Sin este Dockerfile, el pipeline fallaría con make: command not found.
